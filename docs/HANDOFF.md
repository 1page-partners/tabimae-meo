## MEOマガジン

### 機能の目的と利用イメージ

この機能は、旅館・ホテルのマーケティング担当者に、毎月のGBP・MEOの動向と「今月取り組んでほしいこと」を届けるために用意しました。GBPはGoogleビジネスプロフィール、MEOはGoogleマップなどで施設を見つけてもらうための対策を指します。担当者が情報収集に時間をかけすぎず、自施設の改善に着手できる内容として運用をお願いします。

各号は「2026年10月号 MEOマガジン」のように年月単位で管理します。当月のニュースとおすすめチップス（実務のヒント）3件をもとに、AIが「今月のGBP・MEOのポイント」として400〜600文字のまとめ文と重点アクション3件を作成します。文章は旅館・ホテルの担当者向けの親しみやすい口語体で、専門用語には簡単な説明を添え、具体的な行動につながる構成です。

利用者はサービス内で最新号を読み、重点アクションをカード形式で確認できます。過去号は最大12号のアーカイブから閲覧できます。メールではまとめ文・重点アクション・サービスへのリンクを届けます。メールを受け取るかどうかは、利用者が設定画面で選択できます。

### 毎月の運用の流れ

1. 管理者が、GBP・SEO・口コミ・地域集客に関する当月のニュースを、出典URLなどとともに管理画面へ登録します。ニュース収集は現時点では手動です。
2. 「今月号を生成」でAIに下書きを作らせます。自動生成のスケジュールを有効にした場合も、作られるのは下書きまでです。
3. 管理者がプレビューで内容・出典・提案するアクションを確認し、必要に応じて編集して公開します。AIの生成文は確認してから公開する運用でお願いします。
4. 配信対象を確認し、管理者自身へのテスト送信でメールの内容を確認してから、受信を希望する有効施設の利用者へ配信します。
5. 配信結果を確認し、未処理の宛先が残っている場合は再実行します。送信済みの宛先を除いて続きを配信する仕組みです。

画面・DB・生成／配信処理は配置済みですが、実AI生成と実メール送信は未確認です。運用開始前に、後述の外部設定と接続検証をお願いします。

### 画面と実装の概要

| 画面/機能 | 内容 |
| --- | --- |
| `/magazine` | 公開号・最大12号・重点アクションカード |
| `/console/magazine` | コンサルタント用閲覧導線 |
| `/admin/magazine` | ニュース登録、設定確認、生成、プレビュー、編集・公開、対象確認、テスト送信、実配信 |
| `/settings` | 「月次MEOマガジンを受け取る」の保存 |

テーブルは `gbp_tips` / `meo_news` / `meo_magazines` / `magazine_deliveries` / `magazine_recipient_deliveries` / `notification_settings` です。施設の有効性は `facilities.is_active` で管理します。
RLSは認証済みのadminが全操作、consultantがニュース・マガジンをSELECT、userが公開マガジンのみSELECTする設計です。通知設定は本人が保存できます。匿名は閲覧できません。

生成はJST当月のニュースと公開済みチップス3件を参照し、400〜600文字のまとめと重点アクション3件をdraft保存します。同じ年月の既存号は上書きしません。公開済みチップスは10件を本番へ登録しました。ニュースが未登録なら、その旨を明示してチップス中心で生成します。

配信は公開済み号のみ、受信許可された施設ユーザーへ行います。1リクエスト25件まで、送信間隔と時間上限を設けています。未処理があれば管理者が再実行します。成功宛先は再送対象外で、Resendのidempotency keyも使います。全対象者への配信完了後に施設単位の履歴を記録します。

「対象確認」はメールを送らず件数だけを返します。「自分にテスト送信」はログイン中のadminのメールアドレスだけに送信し、通常の配信履歴を変更しません。

### 毎月の自動生成

毎月1日09:00 JST、UTC式 `0 0 1 * *` を想定します。本番はpg_cron・pg_netが無効のため、自動実行はまだ稼働していません。

- Supabase方式: 管理者が拡張を有効化し、Vaultに `project_url` と `service_role_key` を登録して `202610190002_magazine_cron_vault.sql` を適用します。拡張/Secretsがない場合は登録をスキップします。
- GitHub方式: `.github/workflows/monthly-magazine.yml` を用意済みです。Actions Secretsに `MAGAZINE_CRON_SERVICE_ROLE_KEY`、Repository Variableに `MAGAZINE_CRON_ENABLED=true` を登録して有効化します。既定は自動ジョブをスキップし、手動実行にも対応します。

運用する方式をどちらか1つ選び、二重設定しないようお願いします。スケジュールはdraft生成だけで、公開・メール配信は自動化していません。初回実行後は、draftが作成されることまで確認してください。

| 画面が開かない・公開に失敗した | Netlifyの対象サイトのデプロイ履歴・ビルドログと、該当コミット |
| Google連携や生成・配信が失敗した | Supabaseの対象Edge Functionの実行ログ。認証・権限・Secretsの設定状態も確認する |
| データが表示されない・保存できない | SupabaseのDBログ、対象テーブル、ログイン中のプロフィールと施設所属、RLS |
| メールが届かない | Resendの送信結果、送信元の設定、受信設定、宛先別配信履歴、受信側の迷惑メールフォルダー |
| 自動生成されない | 採用した方式の実行記録（GitHub Actions、またはDBのcron・HTTP呼び出し結果）と `generate-magazine` のログ |

フロントの変更が原因の場合は、Netlifyの正常動作を確認済みのデプロイを復旧候補にし、対応するGitコミットを確認してください。ソースを戻す場合は変更を打ち消すコミットを作り、`npm run verify` を通してから公開します。以前のフロントと現在のDB・関数に互換性があることも確認してください。

Edge Functionの変更が原因の場合は、正常動作を確認済みのソースと関連する共有ファイルを揃えて再デプロイします。Netlifyを戻してもSupabaseの関数・DB・Secretsは戻りません。DBは一括で巻き戻さず、変更内容とバックアップの有無を確認して復旧方法を決めてください。バックアップからの復元手順は未検証です。

復旧後は `npm run check:production` に加え、障害が発生した操作を権限のあるアカウントで確認してください。このコマンドだけでは実Google接続・AI生成・メール到達までは確認できません。配信障害では、送信履歴を削除して再送するのではなく、送信済み・未処理を照合してから続きを実行してください。

## 現在の制約と今後の改善候補

現状の制約は以下のとおりです。外部設定・実接続確認の残作業は冒頭の完了条件に沿って進めてください。

- ニュース収集は手動です。自動収集機能はありません。
- 月次自動生成は準備済みですが未稼働です。公開・メール配信は管理者が行います。
- 同じ年月の号は再生成で上書きせず、既存号を返します。内容の変更は編集で対応します。
- メール配信は1回25件までで、未処理分は再実行が必要です。
- Google実接続、実AI生成、実メール送信、スケジュールの初回動作は未確認です。

改善候補として、ニュース収集の自動化、前月ニュースを使う生成期間の設定、未処理メールの自動継続、失敗通知・配信状況の監視を考えています。これらは未実装で、実施時期も未定です。まず現行機能の実接続と運用開始を確認し、その後に必要性・費用・優先順位を私と相談してください。

確認済みの範囲と、これから確認する範囲を分けて記録しながら進めていただければと思います。引き続きよろしくお願いします。
